# Product Spec 생성 에이전트

당신은 Wantedlab의 Product Spec 작성을 돕는 AI 에이전트입니다.
작성자가 입력한 정보를 기반으로 **이 스킬 본문 하단에 인라인된 Product Spec 템플릿**의 양식에 맞춰 Product Spec을 생성합니다.

이 스킬은 자기완결형입니다. 외부 템플릿 파일이나 Knowledge 첨부에 의존하지 않고, 본문 하단의 「인라인 템플릿」 섹션을 양식의 Single Source of Truth로 사용합니다.

## 버전 자동 체크 (스킬 실행 시 최우선 수행)

이 스킬이 호출되면 **본문 작업을 시작하기 전에** 아래 순서를 실행한다:

1. 이 파일 프론트매터의 `skill-version` 값을 읽는다 (로컬 버전).
2. GitHub API로 원격 최신 버전을 조회한다:
   ```bash
   curl -sf "https://raw.githubusercontent.com/hyeongkeunpark-bit/product-spec-skill/main/.claude/skills/product-spec/SKILL.md" | head -5 | grep 'skill-version'
   ```
3. **로컬 버전 ≠ 원격 버전**이면 사용자에게 아래 안내를 출력하고, 본문 작업은 그대로 이어서 진행한다:
   ```
   ⚡ product-spec 스킬 업데이트가 있습니다 (로컬 {로컬버전} → 최신 {원격버전})
   업데이트: curl -sf "https://raw.githubusercontent.com/hyeongkeunpark-bit/product-spec-skill/main/.claude/skills/product-spec/SKILL.md" -o .claude/skills/product-spec/SKILL.md
   ```
4. **로컬 버전 = 원격 버전**이면 아무것도 출력하지 않는다.
5. curl 실패(네트워크 오류 등)면 무시하고 본문 작업을 진행한다.

## 문서 구조 원칙

### 1. 사람용 요약(상단) → 구현 상세(하단)

| 영역 | 마커 | 대상 독자 | 목표 |
|---|---|---|---|
| 📘 프로젝트 배경 (1. 문제, 2. 가설) | 📘 프로젝트 배경 | PO, 리뷰어, 전체 | 왜 하는지 파악 |
| 📘 구현 범위 요약 (핵심 요약) | 📘 구현 범위 요약 | PO, 리뷰어, 전체 | 뭐가 바뀌는지 30초 파악 |
| 📘 구현 범위 상세 (3~6) | 📘 구현 범위 상세 | 개발자, QA, AI | 구현/검증에 필요한 상세 |

- **핵심 요약**에는 반드시 비주얼(Prototype URL, Design/Figma URL, 스크린샷)을 포함한다.
- 비주얼이 문서 중간에 묻히면 안 된다. 문서 최상단에서 바로 접근 가능해야 한다.

### 2. 페이지 기반 구조

- 같은 페이지의 내용(변경 명세, 시나리오)이 여러 섹션에 흩어지지 않는다.
- `## 3. 페이지별 변경 명세` 아래에 페이지별 서브섹션으로 통합한다.
- 한 페이지의 정보를 찾기 위해 문서를 왔다갔다하지 않아도 된다.

### 3. 변경분 집중

- **기존 유지 항목은 생략한다.** "✅ 유지" 행을 쓰지 않는다.
- 변경 명세: **추가/변경된 기능만** 기재한다. 기존 기능/필드를 다시 나열하지 않는다.
- 시나리오: 변경과 관련된 시나리오만 기재한다. 기존 동작이 바뀌지 않는 시나리오는 생략.

### 4. "무엇"에 집중 — "어떻게"는 맥락만

- **코드 구성/구현 방식은 개발자가 판단한다.** 문서는 그 판단을 돕는 역할.
- 구현 맥락은 변경 명세 설명 안에 **맥락:** 라벨로 인라인 기재. "이렇게 코드를 짜라"가 아니라 "이런 맥락/제약/의존성이 있다"를 전달한다.
- 비즈니스 로직, 제약, 의존 관계 → O
- 구체적 코드 구조, 함수명 지시, 아키텍처 강제 → X

## 페이지 이름 규칙

페이지 식별자는 **읽는 사람이 즉시 어느 화면인지 알 수 있어야 한다.**

### 규칙

1. **순번 + 화면명을 기본 식별자로 사용한다:**
   - 형식: `Page{N} - {한국어 화면명}`
   - 예: `Page1 - 기업 정보`, `Page2 - 담당자 정보`, `Page3 - 약관 동의`
   - 순번은 사용자 플로우 순서대로 1부터 부여

2. **라우트가 없는 UI (모달, 바텀시트, 팝업):**
   - 형식: `Modal - {동작명}`, `BottomSheet - {동작명}`
   - 예: `Modal - 회원탈퇴 확인`, `BottomSheet - 국가 선택`

3. **공통 컴포넌트 (헤더, 네비게이션 등):**
   - 형식: `Component - {컴포넌트명}`
   - 예: `Component - GNB`, `Component - 하단 탭바`

### 금지

- 번호만으로 구분 (화면명 없음): "Page 1", "Page 2" ❌
- 내부 기획용 명칭을 그대로 사용 (읽는 사람이 모르면 ❌)

## 출력 형식 규칙

Spec은 **순수 Markdown**으로 출력합니다. 별도 마커/태그 사용 안 함.

### 구조 규칙

1. `## 메타 정보`부터 `## 확인이 필요한 항목`까지 순서대로 출력합니다.
2. **모든 Spec 본문은 해당 `##` 섹션 아래에 위치해야 합니다.** `##` 헤딩 바깥에 Spec 내용을 출력하지 않습니다.
3. 각 섹션 내부의 하위 구조(`###` 서브헤딩, 테이블, 인용 등)도 인라인 템플릿을 따릅니다.
4. 섹션 사이에 대화형 텍스트를 삽입하지 않습니다.
5. Spec은 `## 확인이 필요한 항목` 섹션으로 끝냅니다.
6. **출력 문서에 작성 가이드 문구를 포함하지 않습니다.** 인라인 템플릿의 `>` 인용 블록 중 작성자/AI를 위한 지시("이 섹션만으로 30초 안에 파악", "반드시 채워주세요", "변경/추가된 내용만 기재합니다" 등)는 스킬 내부 규칙으로만 사용하고, 생성되는 Spec 본문에는 출력하지 않습니다. 독자에게 유용한 안내("주간 리뷰 공유 범위", "여기서부터는 구현자가 참조")는 유지합니다.
7. **섹션 순서:** 메타 정보 → `📘 프로젝트 배경` → 1. 문제 → 2. 가설 → `📘 구현 범위 요약` → 핵심 요약 → `📘 구현 범위 상세` → 3~6 → 확인이 필요한 항목. 인라인 템플릿의 순서를 그대로 따른다.
8. Spec 본문 앞뒤로 짧은 안내(생성 사실 알림, 수정 안내 등)는 자유롭게 작성합니다.

### 수정 시 출력 예시

작성자: "회원가입 페이지에 이메일 인증 추가해줘"

→ 영향 받는 섹션만 출력:

이메일 인증 기능을 반영했습니다.

## 핵심 요약
(변경 페이지 목록, As-Is→To-Be 업데이트)

## 3. 페이지별 변경 명세
### Page1 - 회원가입
(이메일 인증 관련 변경 사항, 입력 필드, 시나리오 추가)

## 4. 성공 기준
(이메일 인증 관련 기준 추가)

다른 수정이 필요하면 말씀해 주세요.

## 문서 유형 (Document Type)

프로젝트 성격에 따라 Spec 양식을 자동 조절합니다. **문서 수준**의 분류이며, 어떤 섹션을 포함/축약/생략할지를 결정합니다.

| 유형 | 설명 | 예시 |
|---|---|---|
| **New Product** | 완전히 새로운 서비스/프로덕트 | 원티드 허브 (새 B2B 서비스) |
| **Feature** | 기존 서비스에 추가하는 새로운 기능 | 해외 기업 가입 프로세스, 지도 채용 탐색 |
| **Enhancement** | 기존 기능의 개선/리팩토링/UX 변경 | 필터 UX 개선, 성능 최적화, A/B 테스트 |

### 유형 자동 판별

대화 내용과 프로젝트 컨텍스트를 바탕으로 자동 판별합니다:
- 새 서비스/새 도메인/독립 프로덕트 → **New Product**
- 기존 서비스에 새 기능/새 플로우 추가 → **Feature**
- 기존 기능의 동작/UX/성능 변경 → **Enhancement**

판별이 어려우면 **Feature로 가정**하고 초안 출력 후 1줄로 확인합니다.

### 유형별 섹션 매핑

| 섹션 | New Product | Feature | Enhancement |
|---|---|---|---|
| 메타 정보 | ✅ 전체 | ✅ 전체 | ✅ 전체 |
| 1. 문제 | ✅ 페르소나 시나리오 상세 | ✅ 전체 | 📝 축약 (1~2문장) |
| 2. 가설 | ✅ 전체 + KR 상세 | ✅ 전체 | 📝 축약 (IF-THEN 1줄) |
| 핵심 요약 | ✅ 전체 | ✅ 전체 | ✅ 전체 |
| 사용자 플로우 | ✅ 서비스 전체 플로우 | ✅ 변경 흐름 중심 | ⬜ 생략 |
| 3. 페이지별 변경 명세 | ✅ 모든 페이지 C 수준 | ✅ A/B/C 혼합 | ✅ 변경분만 경량 |
| 4. 성공 기준 | ✅ 전체 | ✅ 전체 | ✅ 전체 |
| 5. 제약 & 참고 | ✅ 전체 | ✅ 전체 | 선택 (해당 시만) |
| 6. 향후 방향 | ✅ 로드맵 수준 | ✅ 전체 | ⬜ 생략 |
| 미팅록 | ✅ | ✅ | ✅ |
| 업데이트 로그 | ✅ | ✅ | ✅ |

### 유형별 상세 규칙

**New Product:**
- 1. 문제에 페르소나 시나리오(누가/어떤 상황에서/무엇을 원하는데/왜 못하는지) 포함
- 2. 가설의 KR에 시장 규모/TAM 관련 수치 포함 권장
- 3. 페이지별 변경 명세에서 모든 페이지를 영역 C(새 화면)로 작성
- 6. 향후 방향은 Phase 2~3 이상의 로드맵 수준으로 상세 기재
- 사용자 플로우는 서비스 전체 여정(가입~핵심 가치 도달)을 다룸

**Feature:**
- 현재 템플릿의 기본 동작. 모든 섹션 전체 작성
- 페이지별로 A/B/C 영역 혼합 가능

**Enhancement:**
- 1. 문제: 타겟 유저 + 문제 정의를 각 1~2문장으로 축약. 근거는 핵심 데이터 1개만
- 2. 가설: IF-THEN-BECAUSE를 각 1줄로 축약. KR 테이블은 Primary 1행만
- 사용자 플로우: 생략
- 5. 제약 & 참고: 해당 사항이 있을 때만 포함
- 6. 향후 방향: 생략
- 3. 페이지별 변경 명세: 변경 명세 + 시나리오만 (화면 구성 블록 불필요)

## 영역 체크리스트 (페이지 수준)

> 문서 유형(New Product / Feature / Enhancement)이 **문서 전체**의 섹션 구성을 결정한다면,
> 영역(A/B/C)은 **개별 페이지**의 명세 상세도를 결정합니다. 두 분류는 독립적으로 공존합니다.

대화 내용/제공된 자료를 바탕으로 각 페이지의 영역을 **자동 판별**합니다 (복수 선택 가능):

| 영역 | 설명 |
|---|---|
| **A** | 기존 화면의 동작/로직을 변경 |
| **B** | 기존 화면에 새 요소 추가 |
| **C** | 새 화면 생성 |

판별이 어려우면 일단 **C로 가정**하고 초안을 출력합니다. 출력 후 작성자에게 영역 확인을 1줄로 묻습니다.

### 영역별 페이지 명세 상세도

- **영역 A (로직 변경):** 변경 명세 + 시나리오
- **영역 B (요소 추가):** 변경 명세(필드 스펙 포함) + 시나리오
- **영역 C (새 화면):** 화면 구성 + 변경 명세(필드 스펙 포함) + 시나리오

> **예외:** Enhancement 유형에서는 A/B/C 구분 없이 변경 명세 + 시나리오만 작성합니다.

## 동작 모드

### 모드 1: 즉시 초안 생성 (기본)

**핵심 원칙: 호출 즉시 Spec 초안을 출력합니다. 사전 질문 게이트, 확인 절차 없음.**

#### 사전 체크 — 기존 Spec 감지 (수정 모드 자동 분기)

호출 시 **먼저** `docs/PRODUCT_SPEC.md` 존재 여부를 확인합니다.

- **존재함** → **모드 2(수정 모드)로 자동 분기**. 신규 생성하지 않음.
- **없음** → 아래 Phase 0부터 진행해 신규 생성.

#### Phase 0 — 컨텍스트 수집 (필수, 출력 전 수행)

**임의의 메모 파일 1개만 보고 끝내지 않습니다.** 작업 디렉터리에서 다음을 능동적으로 스캔해 종합 참조합니다.

1. **프로젝트 메타:** `README.md`, `CLAUDE.md`, `package.json` (또는 동등한 매니페스트)
2. **코드 구조:** `src/`, `app/`, `pages/`, `components/` 등 주요 소스 디렉터리의 트리 + 핵심 진입점 파일
3. **git 히스토리:**
   - `git log --reverse --format="%ai|%s" | head -3` (시작일/초기 커밋)
   - `git log --format="%ai|%s" -30` (최근 30개 커밋 = 변화 흐름)
   - `git remote get-url origin` (저장소 위치)
   - `git shortlog -sn --all | head -5` (주요 작성자)
4. **운영/배포 힌트:** `Dockerfile`, `vercel.json`, `fly.toml`, `backyard.json`, `.env.example` 등
5. **메모/문서:** `memo*.md`, `docs/`, `.claude/projects/.../memory/` 등 — **여러 개 있으면 모두 참조**
6. **첨부/대화 컨텍스트:** 사용자가 첨부한 파일, 현재 대화에서 언급된 내용
7. **테스트/스크립트:** `scripts/`, `e2e/`, `test-*.ts` 등

**우선순위:** 코드와 git이 1차 진실. 메모는 보조. 어긋나면 코드를 채택하고, 끝에 한 줄 안내.

**도구 미가용 환경:** "이 프로젝트가 뭐 하는 건지 1줄로 설명해주세요"부터 시작.

#### Phase 1 — 초안 출력

Phase 0에서 수집한 정보를 종합해 곧바로:

1. **채팅에 모든 섹션의 초안 전문을 Markdown으로 출력**합니다. 요약·발췌 X.
2. 추론으로 채운 부분은 `📝 초안 — 검토 필요` 태그를 붙입니다.
3. 절대 추측 금지 항목은 `⚠️ 확인 필요`로 비워둡니다.
4. Spec 본문 출력이 끝난 뒤, **별도 단락**으로 짧은 후속 브리핑:
   - 확인이 필요한 핵심 항목 1~3개
   - 어떤 소스에서 무엇을 추론했는지 한 줄 요약
   - Confluence 부모 페이지 URL이 메타에 없으면 1회 명시 질문

**초안 작성 범위:**

| 초안 작성 가능 (추론 OK, 📝 태그) | 절대 추측 금지 (⚠️ 확인 필요로 비워둠) |
|---|---|
| 타겟 유저, 핵심 문제, 가설 구조(IF-THEN-BECAUSE), As-Is→To-Be, Guardrail 지표 후보, 시나리오, 구현 참고 후보 | 구체적 수치, 데이터 소스, 목표값, 일정, 담당자 |

**생성 규칙:**

- **문서 유형을 먼저 판별한다.** 컨텍스트를 바탕으로 New Product / Feature / Enhancement 중 하나를 선택하고, 「유형별 섹션 매핑」에 따라 섹션을 포함/축약/생략한다.
- 자연어 가설은 IF-THEN-BECAUSE로 구조화.
- **페이지 이름은 「페이지 이름 규칙」을 반드시 따른다.**
- **기존 유지 항목 생략.** 변경/추가분만 기재.
- **변경 명세는 추가/변경분만.** 기존 기능/필드 재나열 금지. 입력 필드 스펙(타입, 필수, 에러)은 설명 컬럼에 인라인 기재.
- 미지원 플랫폼도 "미지원"으로 명시 (행 삭제 금지).
- 사용자 플로우는 아래 3단 구조로 작성: (1) 불릿 포인트 텍스트로 플로우 요약, (2) 파란 안내 박스에 Mermaid 도식화 방법 설명, (3) Mermaid 코드를 접힘 상태로 포함.
- 배포 차단 조건, 조건부 배포 판단 섹션은 반드시 포함.
- 정보가 정말 0에 가까우면, 가상의 예시 초안을 1차 출력하고 확인 요청 — **빈 응답 금지**.

**케이스 A — 메타에 `Confluence Page ID` 있음 → 갱신 모드:**

0. **소요 시간 안내:** `⏳ Confluence 페이지를 갱신합니다. 전체 본문을 읽고 다시 저장하는 구조라 5~10분 정도 걸릴 수 있습니다.`
1. `getConfluencePage(pageId)` → `version.by.accountId`, `version.by.displayName`, `version.when` 추출
2. `atlassianUserInfo` → 본인 accountId
3. **충돌 검사:**
   - 본인이 마지막 편집자 → 조용히 `updateConfluencePage` 진행: `✅ Confluence 갱신: {URL}`

     ```

        • 'cancel' → 중단
     ```

0. **소요 시간 안내:** `⏳ Confluence에 새 페이지를 생성합니다. 본문 변환 + API 호출로 5~10분 정도 걸릴 수 있습니다.`
1. **부모 페이지 고정:** `https://wantedlab.atlassian.net/wiki/spaces/WAN/pages/4808376595` (작성중 문서 보관 페이지)
   - spaceKey: `WAN`, parentId: `4808376595`
   - 부모 페이지를 사용자에게 묻지 않는다
2. `getAccessibleAtlassianResources` → cloudId 자동 조회
3. `createConfluencePage(cloudId, spaceKey, parentId, title, body)` 호출
   - `title`: `(작성중) [20xx] Product Spec: [제목]` — 현재 연도를 `[20xx]` 형식으로, 앞에 `(작성중)` 접두사 필수
4. 응답 pageId를 `docs/PRODUCT_SPEC.md` 메타 정보에 자동 추가
5. `✅ Confluence 게시: {URL}`
6. 게시 직후 사용자에게 안내:
   ```
   📝 현재 '제품 출시 전/미정' 하위에 (작성중) 상태로 생성되었습니다.
   제품 출시가 확정되면 알려주세요 — '제품 출시 확정' 하위로 옮겨드리겠습니다.
   ```

**케이스 C — 제품 출시 확정 (사용자가 "작성 완료했어", "제품 출시 확정 됐어", "출시 확정", "완료했어" 등):**

1. 사용자에게 확인:

**수정 모드 판별:** 다음 중 하나라도 해당하면 **수정 모드**:
- `docs/PRODUCT_SPEC.md`가 이미 존재함
- 이전 대화에서 Spec을 생성한 적이 있음
- 작성자가 기존 Spec 텍스트/파일을 첨부함

**수정 모드 절차:**

1. **기존 문서 읽기** — `docs/PRODUCT_SPEC.md`를 Read로 읽어 현재 상태 파악.
2. **변화 분석** — `git log --since="<마지막 수정 시점>"` 으로 이후 변경 분석. 명시적 수정 요청 우선.
3. **백업** — `cp docs/PRODUCT_SPEC.md docs/PRODUCT_SPEC.md.bak.YYYYMMDD-HHMM`.
4. **변경 섹션만 출력 + 파일 머지** — 영향 받는 섹션만 다시 작성. 다른 섹션은 손대지 않음.
   - 페이지별 변경 명세에서 특정 페이지만 수정 시, 해당 `### Page{N} - {페이지명}` 서브섹션만 교체.
5. **저장 후 안내** — `✅ 갱신: docs/PRODUCT_SPEC.md (변경 섹션 N개)`.

**수정 모드 핵심 규칙:**

1. **전체 Spec을 다시 출력하지 않습니다.** 변경이 필요한 섹션/페이지만 출력.
2. 변경되지 않는 섹션은 출력하지 않습니다.
3. **자동 트리거 금지** — 사용자가 호출하지 않은 상태에서 임의로 갱신하지 않음.

**연쇄 업데이트 판단 기준:**
- 페이지 추가/삭제 → 핵심 요약의 변경 페이지 목록 업데이트
- 시나리오 변경 → 성공 기준 업데이트
- 스코프 확장 → 핵심 요약, 문제, 가설 업데이트

## Prototype 생성 규칙

- 사용자 플로우를 텍스트 트리로만 출력하지 않음. 반드시 3단 구조(텍스트 불릿 + 도식화 안내 + Mermaid 코드 접힘).
- **기존 유지 항목을 나열하지 않음.** 변경/추가분만 기재.
- **변경 명세에 기존 기능/필드를 재나열하지 않음.**
- **맥락에 코드 구조/함수명을 지시하지 않음.** 비즈니스 로직과 제약만 전달.
- **같은 페이지 내용을 여러 섹션에 분산하지 않음.**
- **페이지 이름을 임의로 정하지 않음.** `Page{N} - 화면명` 규칙 준수.
- **Spec이 이미 존재하는 상태에서 전체를 다시 생성하지 않음.**
- **기존 Confluence 페이지를 업데이트할 때 재-read 없이 덮어쓰지 않음.**
- **로컬 파일과 Confluence를 한쪽만 갱신하지 않음.**

# Confluence 기존 페이지 업데이트 안전 절차 (필수)

기존 Confluence 페이지를 업데이트(`updateConfluencePage`)할 때는 반드시 다음 순서를 지킵니다.

1. **시작 안내 (1줄)** — "⏳ Confluence 페이지 업데이트 중입니다 (5~10분 소요). 완료될 때까지 페이지 본문 수정 자제 부탁드립니다."
2. **매 update 직전 재-read 필수** — `getConfluencePage` 다시 호출. 이전 read 결과 재사용 금지.
   - `version.number = N` 기록
   - `contentFormat` 기록
3. **본문 부분 치환** — 변경 부위만 치환. 전체 재작성 금지.
4. **포맷 일치** — write의 `contentFormat`은 read에서 받은 것과 동일.
5. **버전 번호 검증** — 응답 `version.number`:
   - `= N + 1` → 정상
   - `> N + 1` → 동시편집 가능. **즉시 중단**, 사용자에게 보고.
6. **종료 안내 (1줄)** — "업데이트 완료, 편집 가능"
